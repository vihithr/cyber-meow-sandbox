# ECS / SoA 可行性实验报告

## 结论（先行）

**不建议现阶段把现有 `cat.js` 迁移到 ECS（含 bitECS）。** 依据如下：

1. **游戏实际规模下收益不可感知。** 猫 ≤40、道具 ≤80、粒子 ≤240，合计 ≤360。在这个区间内，SoA 相对 OOP 的全部收益是 **0.07～0.10 ms/帧**，约占 60 FPS 帧预算（16.7 ms）的 **0.4%～0.6%**；在「40 只猫」这一档，两次独立运行甚至出现一次 SoA 更慢、一次更快，差异完全落在测量噪声内。
2. **1.2～1.4× 的倍率来自微基准里最有利的部分，不代表真实收益。** SoA 的优势集中在批量位置更新（O(n) 循环）；真正吃掉时间的是范围查询（O(n²)），而 ECS 不改变算法复杂度。基准中的全配对查询比游戏真实查询重得多（真实场景里猫只扫描约 40 只同类，粒子不做邻居查询），因此本实验已经**高估**了迁移的收益上限。
3. **迁移成本与风险远高于收益。** `cat.js` 为 92,374 字节 / 2350 行，含 10 条行为大计（AGENDAS）、深度耦合的强引用状态机、跨实体状态写入、定时器闭包、外部对象图和直接依赖 OOP API 的测试。为了 <0.1 ms/帧 的收益重写这套系统，成本收益严重不匹配。

## 实验环境与方法

| 项目 | 值 |
| --- | --- |
| Node.js | **v24.15.0** |
| 平台 / 架构 | win32 / x64 |
| CPU | AMD Ryzen 7 7840HS w/ Radeon 780M Graphics |
| 运行方式 | `node --expose-gc experiments/bench.js` |
| 依赖 | 无，纯 Node.js + 原生 TypedArray，未安装任何包 |
| 统计口径 | 预热 2 轮，测量 7 轮取**中位数**；每轮三个实现交错并按顺序轮换；每轮测量前主动 GC |
| 查询半径 | 40，世界尺寸 1280×720 |

三个被测实现：

- **OOP**：`Entity` 对象数组，逐实体调用 `update()` / `countNeighbors()` 方法，字段为普通 JS number（f64）。
- **SoA64**：`Float64Array` 存 x/y/vx/vy、`Uint8Array` 存 state；外部 system 函数批量处理。数值语义与 OOP 完全一致，作为「布局是否为收益来源」的对照。
- **SoA32**：同上但用 `Float32Array` 存位置，即典型的 ECS 内存布局。表中「倍率」= OOP 耗时 ÷ SoA32 耗时。

每个实体每帧执行两个系统：`integrate`（按 state 取阻尼、更新速度与位置、边界环绕，O(n)）和 `rangeQuery`（统计半径 40 内邻居数，O(n²)）。两实现使用同一份固定种子的初始数据、相同帧数与相同运算顺序；构造对象的开销不计入测量（只测稳态逐帧成本）。全部 8 个规模下，三个实现的结果 checksum 完全一致（例如 n=40 均为 88000，n=240 均为 522000），确认计算等价。完整数据见 `results.json`。

## 数据解读

- **ECS 解决的是数据布局问题，不是算法问题。** 本实验里范围查询是 O(n²)，换成 ECS 后仍是 O(n²)。若规模真的成为瓶颈，收益更大的做法是用空间哈希 / 均匀网格把查询降到近似 O(n·k)，这与是否使用 ECS 正交。
- **V8 已经把 monomorphic 对象的字段访问做得很快。** OOP 在积分循环上并没有出现数量级劣势；SoA 在该循环上约 1.5～3 倍的优势只存在于每帧几微秒的绝对量级。
- **倍率不随规模单调上升。** 2000 档倍率反而降到 1.02～1.04×，因为查询在两种布局下都变成内存带宽受限。所谓「实体多了 ECS 就值得」缺乏依据。
- **基准对 ECS 偏有利却仍没有明显胜出。** 基准剔除了对象构造与大部分 GC 成本、使用完全一致的系统函数、并把所有实体都纳入全配对查询；即便如此，游戏规模内的收益仍不足 0.1 ms/帧。

## 迁移 `cat.js` 的成本与风险

以下事实均来自对项目文件的只读检查（未修改任何现有文件）：

- `js/cat.js` 为 **92,374 字节 / 2350 行**，`Cat` 类在 `AGENDAS` 中注册了 **10 条行为大计**（`THRONEC_QUEST`、`TREE_CLIMB`、`AERIAL_PATROL`、`STEALTH_HUNT`、`FEEDER_CAMP`、`MISCHIEF_DEMO`、`BELLY_TRAP`、`SUNBEAM_PILGRIM`、`PARKOUR_CIRCUIT` 及 `NONE`）。`tests/verify.js` 还专门断言了大计数量为 10。
- **强引用状态机**：`this.state` 在数十处被读写，状态字符串众多；`runStateMachine()`、`runAgenda()` 内部大量依赖 `this` 上的即时字段（`stateTimer`、`agendaPhase`、`agendaTarget`、`perchedTier`、`rival` 等）。
- **跨实体直接写入**：`other.vy = -6.5`、`rival.state = 'throne_challenge'`、`rival.stateTimer = 85`、`other.vx = 0`、`other.affection = ...` 等遍布状态机与社交逻辑。SoA 下这些都要改写成通过实体 ID 间接访问，容易引入索引/生命周期错误。
- **定时器闭包**：`setTimeout` 回调捕获 `this`、`other`、`t`（如第 1671、1709 行），无法用纯索引组件表达，必须保留旁路对象表或额外组件字段，抵消 SoA 的紧凑性。
- **外部对象图**：`sceneContext.cats / toys / furniture / mouse / laser / featherWand / spawnParticle`，以及对 `feeder.receiveTap()`、`tree.batDangleBall()`、`sceneContext.toys.splice()` 的直接调用；这些多态对象引用不可能塞进 TypedArray。
- **逻辑与表现字段混用**：`walkCycle`、`tailRootY` 等动画/绘制相关字段在 `update()` 中更新，拆分需要同时改动渲染侧。
- **测试也需重写**：`tests/verify.js` 直接 `new Cat(...)`、调用 `cat.update()` / `cat.runAgenda()` / `cat.pet()`，并断言 `cat.state`、`cat.agendaPhase` 等 OOP 结构；迁移等于同时重构测试套件。
- **额外依赖风险**：引入 bitECS 会增加包依赖、调试与学习成本，而本项目当前是零 npm 依赖的纯前端结构。

综合判断：迁移需要重写状态机分发、10 条行为树、跨实体交互、定时器与外部引用桥接，并同步改造测试，风险和工时都很高；换来的却是约 0.07～0.10 ms/帧 的理论收益。不建议执行。

## 建议阈值

| 场景 | 建议 |
| --- | --- |
| ≤500 个同构实体（**当前项目所在区间**） | 明确不迁移。收益在噪声内或不足 1 ms/帧，重构风险不划算。 |
| 500～2000 个同构实体 | 仍不建议仅为性能改 ECS；先做算法与分配优化（空间划分、避免每帧 `filter`/临时对象），并在真实场景里用 profiler 确认瓶颈。 |
| >2000 个同构实体且每帧执行相同数学运算 | 才值得做一次真实代码内的 ECS 对照实验。注意本实验在 2000 档也只测到 1.02～1.04×，收益上限有限。 |
| 任意规模，瓶颈是 O(n²) 邻居查询 | 优先引入空间哈希 / 均匀网格，收益量级远大于数据布局调整。 |

建议把迁移门槛设为「**稳定超过 1.5× 且绝对节省 >1 ms/帧**」。本实验所有规模都未达到：最高倍率 1.43× 出现在 500 档（A 轮），但 B 轮同档只有 1.08×，无法稳定复现；绝对节省最大约 0.2 ms/帧。


脚本会在 `experiments\results.json` 写出全部原始样本与环境信息。不 `--expose-gc` 也能运行，只是噪声略大。修改 `bench.js` 顶部的 `SIZES` / `FRAMES` / `REPEATS` 可调整规模与统计强度。本实验只在 `experiments/` 目录下新增文件，未修改项目任何现有文件。

## 局限性

- 微基准只覆盖批量积分与范围查询两类系统，不含真实渲染、音频、DOM 与输入处理；这些在游戏里通常比实体逻辑更耗时。
- 测量的是稳态逐帧成本，未计入大量小对象可能带来的 GC 压力（这一点理论上对 ECS 有利）；在 ≤360 实体规模下该因素不足以改变结论。
- 所有数字来自 2026-11-19 在单台 Ryzen 7 7840HS / Windows / Node v24.15.0 上的实测；换硬件或 Node 版本后绝对数字会变，倍数结论应保守看待。
