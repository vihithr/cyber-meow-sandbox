## 1. 背景、范围与方法论边界

### 1.1 为什么需要这份报告

`cyber-meow-sandbox` 是一个零依赖的浏览器沙盒应用：8 个 JavaScript 文件各自用 IIFE 包裹，通过唯一全局对象 `window.CyberMeow` 交换符号，由 `index.html:183-190` 按固定顺序以相对路径同步加载，双击 `index.html` 即可在 `file://` 协议下运行。项目规模不小——`cat.js` 单文件 2655 行、`app.js` 1138 行、`audio.js` 984 行——且同时承载实时渲染、音频合成、行为状态机与物理积分。

这类项目常见的评审困境是：把"文件大""扇出高""有环""每帧分配对象"直接等同于"架构有问题"，并开出重构药方。本报告采用的方法论刻意区分两类问题——**可由依赖图判定的结构/认知复杂度问题**，与**依赖图看不见的表示/实现层问题**——并对前者给出裁决、对后者仅作约束登记，避免混为一谈。

### 1.2 方法论框架：T1 与 T2 的分工

本报告使用"双边界架构"方法论，分两层工作：

- **T1（理论本体层）**：提供关于复杂度管理的规则体系，其核心输入是**模块间的引用关系（依赖图）**。规则按编号组织：H1a/H1b/H2/H3/H4 为硬约束或谓词，D1/D2/D3 为操作与职责划分规则，C2 为经验阈值条件，A1/A2/S3/S5 为公理与偏好。
- **T2（投影绑定层）**：把 T1 的抽象概念绑定到具体项目——确定"模块粒度""什么算公共契约""依赖边如何采集""层语义轴如何选"。没有 T2 绑定，H3"不得依赖未标记的实现形态"之类的规则无法落到具体代码行上。

本次评审的 T2 绑定（来自四份 T2 投影报告）为：

- 模块粒度＝每个 IIFE `js/*.js` 文件为一个模块（8 个生产模块）。
- 依赖边＝按名引用，含加载期解构、方法调用、字段访问。
- 公共契约载体＝**符号级**：`window.CyberMeow.X` 赋值即显式公共暴露面；项目无字段级契约声明、无 API 文档。
- 层语义轴＝**未选定**，属协商程序（theory.md:325-327）。
- H4 逃逸标记＝**全项目不存在**（事实，全仓 grep 无匹配）。

> 这条 T2 绑定是后续 H3/H4 判定的前提。若团队另行声明字段级公共 API，大量"未标记逃逸"判定须改判为契约依赖——这一条件性贯穿全文，不得省略。

### 1.3 证据分层与判定强度

- 〔事实〕/〔推断〕/〔待裁决〕三级标注贯穿全文；表格"证据"列的行号均为事实观测。
- T1 规则自带判定强度元数据，分三类：**机械可判定**（图或标记可算）、**经验可判定**（需变更历史 + 阈值）、**需认知裁决**（依赖组块库或未来演化预测）。三者不互相冒充。
- 表示层观察不使用上述 T1 强度元数据（那是为 T1 规则设计的），统一按事实/推断/待裁决三级标注。

### 1.4 T1 对表示层的失明（本报告最重要的边界）

theory.md §8（第 314-328 行）是本报告的总闸门，三句原文逐句适用：

1. 第 320 行把表示/实现层定义为"一个契约在其承载介质中如何被实现（以值还是以引用承载状态、是否可复制、是否可并行、是否受平台不变量约束）"，并声明其对本理论**正交、结构性失明**。
2. 第 322 行指出依赖图的输入通道"只记录'谁按名引用谁'，不记录'该引用以何种语义承载、是否分配、是否可 fork'"。
3. 第 323 行的正交性推论："本理论推荐的任何拓扑操作都不决定其表示层实现……表示层问题既不能由本理论裁决，也不构成本理论的反例。"

由此得出本报告的强制性纪律：

- **渲染、内存、分配、并行、序列化格式、加载介质、Web Audio 节点生命周期、DPR、帧序、DOM mock 等全部落在表示层，T1 结构性失明。**
- 性能收益（帧率、GC、缓存局部性）一律**不**写作 T1 推论，也不作为架构合法性的证据或反例。
- 表示层对象对拓扑重构只有**约束**关系（重构必须保持这些不变量），没有**裁决**关系（T1 不能说这些不变量该如何改）。
- 按 SKILL.md 的 Coverage Status 口径，第 4 节全部条目统一标记为 `Out-of-scope`。

### 1.5 范围之外

- `tests/` 全部排除出生产模块的 H3 统计；`experiments/`、`server.py`、CSS、HTML 非生产依赖面。
- 本报告不修改任何项目文件，也不执行会改变项目状态的操作；所有验证命令作为"可证伪验证"列于第 6 节，供后续执行。

## 4. 性能痛点（表示层实证，与 T1 裁决明确分开）

> **适用域声明（先于所有结论）**：本节全部内容落在 theory.md §8（第 314-324 行）声明的表示层——渲染、内存、分配、并行、平台不变量、序列化格式。按第 1.4 节的强制纪律，这些发现**不由 T1 裁决、不构成 T1 反例、不登记为 T1 推论**；Coverage Status 统一为 `Out-of-scope`。所有量级数字均为代码推导的运算/分配次数（推断），**不是毫秒或 FPS 实测值**；会过期的指标快照集中放在附录 A（标注日期 2026-11-20）。

### 4.1 渲染热路径

- 〔事实〕**每帧渐变创建**：腿部近端线性渐变每可见猫每帧恰好 2 次（`cat.js:585` 在 `_drawLegMesh` 内直接调用，`:1323-1324/1466-1467`；远端 `isFar=true` 被 `:584` 排除）；重点色口鼻径向渐变每只重点色可见猫每帧 1 次（`cat.js:974-978`）。两者坐标逐帧变化，无法用固定 key 缓存。
- 〔事实〕**缓存 key 动态致失效**：远眼宝石渐变 key 含 `rx.toFixed(2)`（`cat.js:776`），而 `turn` 逐帧变化（`:847/1586`），头部转动期间每猫每帧最多新增 1 条永久 Map 记录；`_gradCache`（`:496`）全文件无清理路径。〔推断〕长时间会话中 Map 单调增长，属表示层内存/GC 成本。
- 〔事实〕**微毛发 pattern**：共享 tile 只建一次（`cat.js:273-289`），但 `createPattern` 每次调用都执行（`:294`），`render()` 每帧每猫调用（`:1200`），即每帧 N 次 `CanvasPattern` 分配；low 档为 0。
- 〔事实〕**shadowBlur 分布**：激光点 blur=20 每帧 1 次（`app.js:1088-1090`）；萤火虫 blur=8、60 个弧共用一次状态设定（`environment.js:302-319`）；对话气泡 blur=8（`cat.js:1141-1156`）。均在末尾显式复位 `shadowBlur=0`。
- 〔事实〕**视口裁剪**：`_isVisibleX`（`app.js:843-846`）应用于家具/玩具/猫/文字粒子（`:1054/1067/1076/1107`）；天气粒子与阳光不经过裁剪（`:1040/1043-1046`），其成本不随可视宽度收缩而下降。
- 〔事实〕**背景缓存**：签名 `theme|worldWidth|height|dpr`（`app.js:887`），余量 420px（`:890`），越界重建并强制渐变缓存失效（`:903`）；每帧 1 次源矩形 `drawImage`（`:945-960`）。`_ensureStaticFurnitureLayer`（`:926-940`）全文件无调用点，当前不分配。

**已正确的优化（事实）**：胡须 6 根合并 1 次 stroke（`cat.js:1058-1065`）、虎斑合并 2 次 stroke（`:1408-1417`）、key 稳定的渐变走缓存（`:811/889/932/1039/1369/1393/1439`）、背景渐变按 key 缓存（`environment.js:145-173`）。

### 4.2 状态机与物理热路径

- 〔事实〕**双时间基**：平滑/计时类用 dt（`cat.js:1509-1624/1856/2040`），但物理积分 `cat.js:1673-1684`、爬树 `:1664-1665`、随机冲量 `:1647-1648`、反弹 `:1727` 均按固定每帧增量；家具/玩具的 `update` 签名根本不接收 dt（`furniture.js:35/101/203/…`、`toys.js:28/151/237/…`）。〔推断〕30 FPS 下物理演化约为 60 FPS 时的一半，120 FPS 下相反——这是刷新率一致性/确定性问题（§8 平台不变量），不是 T1 推论。
- 〔事实〕**扫描热点**：唯一明确的 O(C²) 全对扫描为 `checkSocialInteraction`（`cat.js:2263-2294`，上限 40×39＝1560 次 hypot/帧，受 300 帧冷却抑制）；`evaluateSensors`（`:2321-2381`）同帧对同一数组 5 次全扫（上限约 13,600 次/帧）；落脚面扫描 `:1688-1717`（O(C×F×S)）、水洼检测 `:1814-1833`、Roomba 推撞 `furniture.js:250-270`、投喂机 `furniture.js:650-657` 叠加。〔推断〕上限场景每帧实体间访问约 2–3 万次；默认 3 猫约 1–2 千次。这是运算次数，非耗时。
- 〔事实〕**不可达分支**：`CatSuspensionBridge.type='bridge'`（`furniture.js:751`），但 `cat.js:1705/2464` 以 `'suspension_bridge'` 判定，全 `js/` 无该类使用——故 `onBridge` 恒为 false，`checkBridgeDuel`（`:2049/2197`）等分支当前不可达，相关 O(C²) 为零成本。若修复字符串，该分支将成为真实热点。属功能/可达性问题。
- 〔事实〕**每帧分配**：`currentLookTarget`（`cat.js:1559`）、`getTip()` 新对象（`toys.js:349-352`，`cat.js:1561/2073/2330`）、`evaluateSensors` 目标字面量（`:2326+`）、毛线球 trail（每帧 `unshift`，`toys.js:50`，长度上限 14）；渲染路径每猫每帧约 80–120 个短生命周期对象（推断）。缓存设计总体正确（`:495-512` 渐变、`furniture.js:22-33/380-396` 落脚面），但 `cat.js:1690-1693` 的内联 fallback 绕过缓存，是潜在失效口。

### 4.3 音频、UI、环境与存档

- 〔事实〕**音频清理路径完整**：总线节点幂等创建（`audio.js:204-230`）、一次性音源 `onended` 断链（`:39-48`）、持续声源淡出断链（`:394-427/667-688`）、`dispose` 幂等（`:159-202`）、可见性挂起/恢复（`:96-157`）。未发现确定性无界节点累积。一次性音源按调用分配、噪声缓冲逐样本填充（`:456/487/615/811-818`）属短生命周期 churn，不构成泄漏结论。〔待裁决〕suspended 状态下 `onended` 时机依赖浏览器实现。
- 〔事实〕**重复定义**：`playSlap`（`audio.js:513` 与 `:873`）、`playChatter`（`:534` 与 `:851`）各定义两次，按 JS 类语义后者覆盖前者——`playChatter` 的 `pitchMod` 形参（`ui.js:643`、`cat.js:1774/1911/2281/2313/2633` 的调用）实际不可达。这是代码结构事实，成因属认知域。
- 〔事实〕**定时器与 DOM**：所有具名定时器有清除路径（`audio.js`/`ui.js`/`app.js` 各若干，见输入证据）；主循环 `app.js:989-1127` 不写 DOM，DOM 写入最高频为 1Hz（`ui.js:298-308` 挑战 HUD）。〔推断〕未发现逐帧 DOM 抖动或定时器泄漏。
- 〔事实〕**粒子池**：主粒子上限 240（`app.js:40`）、微尘 60、雨滴 80、猫/玩具/家具 40/80/60 均有硬上限；唯一无上限的是侍奉台粒子池 `studioParticles`（`ui.js:408/563/593-602/611/628/648-656`），靠约 40 帧衰减与距离节流（`:528/852-865`）收敛。〔推断〕属防御性缺口，非已观测泄漏。
- 〔事实〕**存档**：`saveState` 同步序列化 6 字段写单键 `cybermeow_cats_save`（`app.js:766-778`），4 个调用点（`:378`、`ui.js:178/190/441`），异常静默吞掉（`:777`）。〔待裁决〕`file://` 下 `localStorage` 可用性随浏览器配置而异，代码无降级路径，需实测。

### 4.4 基准数据与真实浏览器的差距

- 〔事实〕**基准口径**：`tests/bench.js` 在 VM 中用 `tests/dom-mock.js` 手动推进 rAF，固定 1920×1080/DPR2、300 帧，并主动把 EMA 钉在 16 以**屏蔽自适应画质**（`:66-74`）；`drawImage` 与路径方法只递增计数器（`dom-mock.js:17-23/73-82`），渐变只返回 `{addColorStop:noop}`（`:43-54`）。因此 JS 耗时近似"遍历+调用+分配"时间，**不含任何像素工作**。
- 〔事实〕**ECS/SoA 实验**：`experiments/results.json` 重算显示实际规模（≤360）SoA 收益 0.07–0.10 ms/帧，占 16.7ms 预算 0.4–0.6%；查询主导项占 98.9%（n=360）；n=2000 时 SoA32 反慢于 SoA64（倍率不随规模单调上升）；checksum 三方一致。〔待裁决〕"不建议迁移 ECS"属需认知裁决（成本收益＋未来演化），数据只给收益上界，不强制决策。A 轮倍率未保存到 results.json，无法独立复核。
- 〔推断〕**mock 与 GPU 差距**：计数≠像素工作；DPR2 对应 829 万像素的全屏 `drawImage` 在 mock 中只 `+1`；high/low 的真实差值不可由 Node 数据判定；`hrtime` 不含 vsync/合成/GPU 提交。详见附录 A 的 12 项"测不到"清单。
- 〔待裁决〕**验证手段**：以 Chrome Performance 面板录制真实游玩，用 p95 帧时间与掉帧率（而非均值）作主指标，分别录制 high/low/auto 三档；未出浏览器数据前不得据 Node 数字下结论。
